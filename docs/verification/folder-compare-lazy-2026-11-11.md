# 폴더 비교 범위 및 응답성 수정

사용자 보고 후 Windows Application 로그에서 OmniEdit 1.11.16의 AppHangB1 기록을 확인했다. 예외 충돌 로그는 없었다. 사용자가 선택한 정확한 두 경로는 확인하지 못했으며, 별도의 대량 파일 자료로 응답 없음 현상을 재현했다.

## 변경

- 현재 폴더의 바로 아래 파일·폴더만 조회한다. 하위 폴더는 더블클릭/Enter로 진입할 때 비교하고 상위 폴더 버튼으로 위치·선택을 복원한다.
- 양쪽 폴더 이름이 같아도 내부를 동일하다고 판정하지 않는다. 한쪽 전용 폴더는 반대쪽을 가상 빈 위치로 열며 저장 전에는 디스크에 폴더를 만들지 않는다.
- 세 목록에 행별 알림을 보내던 처리를 한 번의 데이터 바인딩으로 바꿨다. 파일 비교 버퍼는 재사용하고 빈 파일은 크기 0 확인 후 동일 판정한다.

## 재현 및 확인

동일한 빈 파일 50,000쌍을 실제 임시 디렉터리에 생성했다. 전체 내용은 0바이트이므로 파일 용량이 아닌 항목 수의 영향을 분리한 검사다. UI 타이머의 최대 실행 간격과 프로세스 누적 할당량을 측정했다.

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 비교·화면 표시 | 40.412초 | 28.971초 |
| UI 최대 실행 간격 | 6,550ms | 122ms |
| 누적 관리 메모리 할당 | 12,165,687,528바이트 | 1,517,816,160바이트 |
| 최대 프로세스 작업 집합 | 202,784,768바이트 | 196,497,408바이트 |

누적 할당량은 동시 점유 메모리가 아니다. 디스크 조회 시간은 환경에 따라 달라지며, 수정 후에도 비교 전체 시간 동안 취소 가능한 백그라운드 작업으로 실행한다.

- Core 44/44: 단계별 폴더 진입, 파일/폴더 충돌, 접근 오류, 바이트 비교, 256MiB 스트리밍 비교·읽기 중 취소, 버퍼 재사용 포함.
- 비어 있지 않은 파일 1,000회 비교의 누적 할당 2,369,968바이트(32MiB 상한).
- UI: 같은 폴더 탭에서 진입·상위 이동, 한쪽 전용 폴더의 미생성, 파일 새 탭, 저장 후 상태 갱신, 선택·스크롤 동기화 검증.

실행 명령:

```powershell
dotnet run --project tests/MyTextEditor.Core.Tests -c Release --no-build --no-restore
dotnet run --project tests/MyTextEditor.Performance -c Release --no-build --no-restore -- --folder-compare
dotnet run --project tests/MyTextEditor.Performance -c Release --no-build --no-restore -- --folder-stress --files=50000
```

수치 원본은 `artifacts/folder-compare/stress-before.json`, `stress-after.json`이다. 이번 수정은 로컬 개발본이며 기존 GitHub 릴리즈를 덮어쓰지 않는다.
